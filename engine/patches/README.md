# Engine patches

`engine/quickjs-ng` is a git submodule tracking upstream QuickJS-NG unchanged.
Every change we make to the engine lives here as a patch, applied to that
submodule's working tree by `scripts/apply-patches.js`.

| `0073` | Stores typed-array elements from the element-store handler | The opcode's inline arm covers only fast arrays, so every other element store leaves the interpreter for a call that re-derives the class the handler already resolved, and pays the frame publication and operand re-fetch around that call | A guarded arm writes integer and float views directly; the helper is out of line so its switch over the view classes does not sit in the interpreter body | Typed-array element stores ~9% faster; octane +1.1%, react -0.3%, minireact -0.7% against the stock engine | No |
| `0074` | Inline the intrinsic typed-array length getter in OP_get_length | The generic path re-checks the receiver and the property after the handler has already resolved both, for a value that only depends on the element count | The arm requires an integer or float view whose `length` is still the prototype accessor, so an own `length` shadowing it keeps the slow path, as do read-only views, detached buffers and every other class. The value returned is the element count, matching the accessor the arm replaces | No. |
| `0075` | Skip the global_var_obj probe when its shape is empty | The lookup walks the variable object on every global read, including when that object is empty, which is the state of a program that declares no global variables | An empty shape check is taken before the probe. A shape that is not empty takes the existing path unchanged, and a missing name still produces the same reference error | No. |
| `0076` | Cache the global name resolution of OP_get_var | Resolving one global name probes two objects and walks their hash chains -- ctx->global_var_obj for a global lexical binding, then ctx->global_obj for a `var` or function declaration -- and publishes the current pc through sf->cur_pc before calling out, on every execution of the opcode | A 128-set, 2-way table keyed on the low bits of the atom, memoizing "this atom is own data property #offset of this object". A hit returns a new reference to the same slot the probe would have found | No. |
| `0077` | Skip the @@hasInstance lookup for a plain function in instanceof | JS_IsInstanceOf always performs Get(obj, @@hasInstance), calls the resulting C function and converts its result to boolean, on every instanceof. For a plain bytecode or C function that lookup can only resolve to the built-in js_function_hasInstance, whose entire body is a call to JS_OrdinaryIsInstanceOf -- so the property lookup, the C-function dispatch and the ToBool round trip all happen for nothing | A class test, a prototype test and an own-property test, then a direct call to JS_OrdinaryIsInstanceOf. | No. |
| `0078` | Compare a Number and a BigInt without losing the sign | The mixed path reduced both operands to a common form before ordering them, which loses which operand is negative and can report the order inverted | The comparison takes account of which operand is negative and which representation it holds before deciding the order. Values that are equal compare equal, NaN keeps its unordered result, and same-type comparisons are untouched | No. |
| `0079` | Compare a rope string against a BigInt as a string | A string operand compares by string, and a rope reaches the wrong arm because its representation is not the flat string the classification expects | The rope is resolved to its string before the operand kinds are classified, so a rope that resolves into a numeric-looking string still compares as the string it is. Ordinary strings, non-rope operands and string-to-string comparisons take the existing path | No. |
| `0082` | Spread an ordinary object by walking its shape | Collecting the keys allocates an array and re-walks the properties that the shape already holds in order | The walk reads each property's atom, flags and value from the shape, skipping non-enumerable properties and following the property array for the values. A proxy, a module namespace and any receiver whose shape can change during the copy take the existing path, so accessors and exotic objects keep their observable order | No. |
| `0083` | Pin a for-in source's shape instead of materialising its keys | The snapshot allocates per loop and duplicates state the source's shape already describes | A pinned shape keeps the source alive and is validated on each step, so a mutation that invalidates it abandons the pinned walk and hands the loop to the existing implementation, which has already seen every key the pinned walk produced. Proxies, arrays with holes and receivers with accessors are not pinned | No. |
| `0084` | Answer the for-in prototype-chain question without allocating | The walk collected every own key of each prototype into an array and inspected the result, so a level that contributes nothing still cost an allocation and the collection of all of its keys | A noinline helper that reports whether a level has an enumerable string-keyed own property: 1 yes, 0 no, -1 for an exotic object the scan cannot judge, where the caller keeps the original allocating path. It reads the shape directly and tests each candidate atom's kind without a call | No. |
| `0085` | Avalanche the Map and Set key hashes | A hash whose high bits are not spread leaves the bucket determined by a few low bits, so the container degrades toward a linear scan for keys that share them | A finalisation step spreads each bit of the incoming hash across the whole word before the bucket is selected. Insertion, lookup and deletion all run the same function, so they stay consistent, and keys that compare equal still hash equal | No. |
| `0086` | Grow the property array by doubling | A fixed increment reallocates once per property added, so an object that accumulates many properties reallocates a linear number of times | Reallocation follows a geometric schedule and the excess capacity is dropped by the existing compaction path when the object settles. Small objects keep the same initial capacity, and property indices, hash links and shape identity behave as before | No. |
| `0087` | Skip ArraySpeciesCreate when it provably ends at a plain array | The lookup runs for every array result even when the intrinsic constructor and species make the answer fixed | The guard admits a receiver whose constructor is still the intrinsic Array and whose species has not been replaced. A subclass, a replaced constructor, a replaced species, an own species property or a proxy takes the existing path, so an observable constructor read is never skipped | No. |
| `0088` | Object.assign must not use the object-spread fast path | The spread walk defines properties, while assignment runs a setter on the target, refuses a read-only target in strict mode, and orders the copy as the assignment operation does | Object.assign uses the assignment operation for each source property, so a setter runs, a read-only target throws as it should, and property order and enumerability are those of the assignment. Object literals with a spread keep the shape walk they already had | No. |
| `0089` | Memoize the (shape, key) to index mapping for element loads | Repeated loads on the same layout repeat the walk that found the slot | The memo holds a counted reference to the shape, so it cannot outlive the layout it describes, and it is consulted only for a receiver whose shape still matches. A miss, a shape change, a proxy and any receiver the fast element path already declines take the existing path | No. |
| `0090` | Memoize the for-in pin admission scan per shape | The scan repeats for every loop over the same layout, and its answer is a property of that layout | The memo holds a counted reference to the shape, which keeps the answer tied to the layout it was computed for, and an answer is reused only while the shape is unchanged. A refused source stays refused and is not re-scanned | No. |
| `0091` | Pass the original object as the receiver in the borrowed field load | The variable that holds the borrowed receiver is reassigned by the walk to the exotic object it stops on, and the slow path then handed that object on as the receiver | The slow path reads the receiver back from the frame slot the load borrowed it from, instead of keeping a second local alive for the whole handler. A proxy's get trap and a getter on a prototype now observe the object the program named | No. |
| `0092` | Do not build a stack trace for thrown values that cannot carry one | Frames were collected before it was known whether the value could carry them, so a thrown primitive, plain object or thenable paid for a complete stack walk with string formatting, on a path that programs use for control flow. Only a reporter that reads the slot through js_std_cmd(ErrorBackTrace=2, ...) could observe it, and nothing in this runtime does | One condition with one clause fewer: `needs_backtrace()` decides on its own. | No. |
| `0095` | Defer Error stack-string formatting to the first `.stack` read | Formatting the text when the Error is constructed spends that cost even for the errors whose stack is never read | An internal class holds the frames, each retaining a name reference, a filename atom and two positions, with a finalizer that releases them; nothing retained is an object or a bytecode, so an Error cannot keep a function alive | No. |
| `0096` | Take acyclic function bytecodes off the collector's object list | The collector visits each code object twice per collection to account for one edge, and a code object with an empty constant pool, no object-literal table and no inline-cache table cannot take part in a cycle | The predicate is evaluated when the object is created and re-evaluated where one of its terms changes, never per collection, and the default is traced. The realm reference stays counted, so a context cannot be freed while code names it | No. |
| `0097` | Admit lazy function bodies to the untraced set | A deferred body reserves its constant pool inline from the header and skips the rest, so the pool count is non-zero for a pool that has never been written and the pool-count term excludes the objects the deferred reader creates | The reserved slots are all the integer zero, because the reader's allocation zeroes them and nothing writes the pool before the body is materialized, so marking one does nothing; that is the same fact the free path already depends on | No. |
| `0098` | Report the traced GC population and its composition | The object count that was reported covers only JS objects and is a strict subset of the population the collector walks, so a cost derived from it is attributed to the wrong denominator, and the two differ by an amount that depends on the heap | The counts are taken before the branches that skip most GC types, so every traced object is counted once, and they are produced by the loop that already walks the heap. Nothing is added to a hot path and no behaviour changes | No. |
| `0099` | Pace cycle collection by whether the last collection reclaimed anything | The rearm is a function of heap growth alone and never asks whether the collection it just paid for reclaimed anything. Everything acyclic is freed at its last decrement without the collector, so a collection finds nothing at all unless the program built a cycle | A collection is unproductive when it reclaimed less than 1/64 of the heap, or less than 256 KB absolutely. | No. |
| `0100` | Clear the operand-stack slot before a helper consumes the value it names | Those helpers hand the operand to a conversion that consumes the reference and then convert the other operand, which can run user code. From the first call until the result is stored, the slot names a value the helper no longer owns, so anything that inspects the operand stack during that window reads a stale reference | Nine two-operand sites clear both slots and three single-operand sites clear the one, at the point where the reference moves rather than after the conversion returns. | No. |
| `0101` | Borrow frame receivers for element loads | Computed element reads otherwise duplicate the receiver, push and pop a stack slot, dispatch its load, and release it immediately | A scan over the pre-resolution instruction stream admits a window whose simulated operand depth reaches the consumer without crossing a label, a branch, a call, a receiver write, or a slot that closures, eval, with or a referenced arguments object can reach. The rewrite deletes the receiver's push and emits a borrowed-receiver element load carrying the frame slot instead | Yes. |
| `0102` | Borrow frame receivers for element stores | The store pays the same duplicate, push, dispatch and release as the load, for a receiver the frame already owns | The same window scan recognises a store whose receiver sits at the simulated depth below its key and value, admits nested element loads inside the window, and emits one combined store opcode that selects the local or argument register file from its operand. The receiver stays in its frame slot, the key and value are consumed exactly once, and the slow property path takes a real reference before it can run user code | Yes. |
| `0103` | Move the operand-shuffle handlers out of the interpreter's dispatch body | Each inline case declared a temporary JSValue and performed the shuffle inside JS_CallInternal. Every such local enlarges that function's stack frame and every such body adds to its code, and both are paid on every interpreted call, whether or not the shuffle executes | Eight noinline helpers -- perm3, rot3l, rot4l, rot5l, rot3r, perm4, perm5 and swap2 -- whose bodies are the shuffles the cases performed, each replaced by a single call. | No. |
| `0104` | Moves 25 cold handler bodies out of the interpreter's dispatch body | Each inline case declared its own temporaries inside JS_CallInternal, so every one of them enlarged that function's frame and its register pressure on every interpreted call whether or not it ever ran. Outlining them takes 29.6% off the symbol, 28.6% off the frame, and 38% off accesses to the interpreter's own spill area | 25 `static no_inline __attribute__((cold))` helpers; every dispatch case becomes a call plus a constant `pc` advance | No. |
| `0105` | Breaks the closure self-cycle at frame teardown | About half of everything the collector visits | `js_closcyc_frame`, called from the teardown after the locals are released and while the frame still owns its var_ref list, which is the only moment the stranded pair reads as two count-1 objects | No. |
| `0106` | Retires three element and branch fusions whose A/B was null |  | Stops emitting `for_in_next_if_false`, `get_arg8_loc8_array_el`, and `get_loc8_array_el`, retaining their numbered slots as reserved opcodes | No. |
| `0107` | Adds an experimental register-bytecode backend and interpreter, guarded by `QJS_REGVM` | The operand-stack interpreter pays a frame load and a frame store for every local and argument and a push and a pop for every temporary; a register form removes that traffic at the source, and this is the experiment that decides whether it beats the stack VM on the code react-native-quickjs runs | `quickjs-regvm.h`, `js_regvm_scan`, `js_regvm_build_cfg`, `js_regvm_encode`, `js_regvm_execute`, and the three `builtin-*.regvm.h` blobs | Yes. |
| `0108` | promotes register variables into fixed homes | Phi copies dominate register move traffic. Aliased values at joins and handlers that consumed read-only operands made home allocation unsafe until those paths were corrected | Home selection, overlap splitting, register compaction, and checks that refuse unsafe functions. It also makes optimization use counts include join inputs and retains register ownership for read-only operands | No. |
| `0109` | fixes register value aliasing, iterator close and two reference leaks | The stack-shaper alias change left `nip` without a value definition and left the slot-forwarding model naming shaper outputs as fresh values, so logical assignment and `yield*` results read stale registers. The for-await step's `dup3 | `nip` in the shaper alias table, alias-aware slot forwarding, a sentinel drop only on the last stack reference, and borrowing calls to JS_DefineGlobalFunction and JS_DefineProperty | No. |
| `9999` | Raises the bytecode version number, once, for every patch above that needs it | Bytecode built by a patched engine must not load in an unpatched one. Doing it here rather than in each patch stops patches colliding on the same line | - | This is the bump |
The table below is the whole fork at a glance. You should be able to understand
what we changed and why without opening a single `.patch` file.

## Writing a patch header

Headers are for people. Keep them short -- usually twenty to forty lines --
and say things the way you would say them out loud.

```
Subject: <one sentence saying what this adds>

What this does
  Two to four short sentences.

Why we need it
  What in the current engine is broken or impossible without this.

What it adds
  JS_GetFrameInfoAtLevel()  - asks the engine where a given stack frame is
                              in the source: which file, which line, which
                              column, and the function's name.

Needs a bytecode version bump
  No.

Notes
  Anything a reviewer genuinely needs. Leave it out if there is nothing.
```

Rules:

- Spell acronyms out the first time. Write "the Chrome DevTools debugging
  protocol", not "CDP".
- No decoration. No symbols, no shouting in capitals, no bookkeeping about
  which branch or session produced it.
- Nothing a stranger cannot follow. No references to internal documents, and
  no using a patch number as if it were a name.
- Describe behaviour, not internals. "Lets the debugger ask where each stack
  frame is" beats a paragraph about borrowed atoms. Details like who frees
  what go under **Notes**, if they matter at all.
- If the patch exists for speed, show the measurement.

## No patch bumps the bytecode version

A patch that changes the bytecode format **must not touch `BC_VERSION`**. It
says so in its header and in its README row, and changes nothing.

One patch raises the number, once, for the whole series:

    9999-bc-version-bump.patch

It is numbered `9999` so that adding patches never renumbers it and it always
applies last. Its header lists every patch that made the bump necessary.

The reason is not tidiness. If each patch bumps the version itself, then any
two such patches conflict over the same line for reasons that have nothing to
do with what either one does, and rebasing the series becomes a day's work
instead of a minute's.

The precompiled `builtin-*.h` blobs record the bytecode version in their first
byte, so they are regenerated *after* the tail patch, as part of the projection
step — never inside the patch that changed an opcode.

`scripts/apply-patches.js --check` enforces all of this. It fails if a patch
has no row in this table, if a row names a patch that does not exist, if any
patch other than `9999` touches `BC_VERSION`, or if a patch says it needs a
bump while `9999` is missing.
