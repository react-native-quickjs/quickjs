# Engine patches

`engine/quickjs-ng` is a git submodule tracking upstream QuickJS-NG unchanged.
Every change we make to the engine lives here as a patch, applied to that
submodule's working tree by `scripts/apply-patches.js`.

| `0073` | Stores typed-array elements from the element-store handler | The opcode's inline arm covers only fast arrays, so every other element store leaves the interpreter for a call that re-derives the class the handler already resolved, and pays the frame publication and operand re-fetch around that call | A guarded arm writes integer and float views directly; the helper is out of line so its switch over the view classes does not sit in the interpreter body | Typed-array element stores ~9% faster; octane +1.1%, react -0.3%, minireact -0.7% against the stock engine | No |
| `0074` | Inlines the intrinsic typed-array `length` getter in `OP_get_length` | `typedarray.length` is a native accessor, so the opcode's arm for an own data property stops at the receiver's exotic bit and calls `JS_GetPropertyInternal` -> `js_call_c_function`, whose whole body is `return js_int32(count)`, after re-walking the chain the handler already walked | Not benchmarked individually; adjudicated with the cumulative stack | No |
| `0075` | Skips the `global_var_obj` hash probe when its shape is empty | `global_var_obj` holds only global lexical bindings (`let`/`const`/`class` at script top level), so `var`-declaring code probes an empty shape on every `OP_get_var`, `OP_get_var_undef` and `OP_put_var`; a test on the same shape, in the same call, decides whether the probe can find anything | Not benchmarked individually; adjudicated with the cumulative stack | No |
| `0076` | Caches global name resolution in front of `OP_get_var` | Resolving one global name probes `global_var_obj` then `global_obj`, walking both hash chains and publishing `sf->cur_pc`, on every execution | A 128-set, 2-way cell table invalidated by a runtime generation counter bumped from `add_property`, `add_shape_property` and `js_shape_prepare_update` | Not benchmarked individually | No |
| `0077` | Skips the `@@hasInstance` lookup in `instanceof` for a plain function | `JS_IsInstanceOf` always does `Get(obj, @@hasInstance)`, calls the result and converts it, and for a plain function whose `[[Prototype]]` is `Function.prototype` with no own `@@hasInstance` that lookup can only reach `js_function_hasInstance`, which just calls `JS_OrdinaryIsInstanceOf` | A class test, a prototype test and an own-property test, then a direct call; `Function.prototype[@@hasInstance]` is non-writable and non-configurable, so no invalidation is needed | Not benchmarked individually | No |
| `0078` | Fixes the inverted answer for mixed Number/BigInt comparisons with a negative operand | `js_bigint_float64_cmp` inverts the result when the operand is negative and the exponents differ, so `-0.5 < -1n` reported true and `-1n < -0.5` reported false | Corrected sign and exponent handling | Correctness fix, not benchmarked | No |
| `0079` | Compares a rope string against a BigInt as a string | `js_relational_slow` coerces a rope as a Number before comparing it with a BigInt, so `<` and `==` disagree about the same value | The rope takes the string comparison path like a flat string | Correctness fix, not benchmarked | No |
| `0082` | Spreads an ordinary object by walking its shape | React builds props by spreading on every render, and the generic path allocates an array of every own property name, takes and releases an atom reference per property, then looks each name up in the source | A direct walk of the source shape when both sides are ordinary objects; getters, Proxies, symbol keys, non-enumerable properties and non-object or altered-prototype sources keep the generic path | Not benchmarked individually; adjudicated with the cumulative stack | No |
| `0083` | Pins a `for-in` source's shape instead of materialising its keys | Every execution rebuilt the enumeration: two allocations, a scan of `Object.prototype`, a name array with an atom reference per key, and one full has-property lookup per key yielded | A counted reference to the source shape when the source is an ordinary object whose keys come from its shape alone, whose shape is hashed, and which has no enumerable array-index, symbol or var-binding key; the walk then skips the name array and the per-key lookup | Not benchmarked individually; adjudicated with the cumulative stack | No |
| `0084` | Answers the `for-in` prototype-chain question without allocating | The old answer scanned the prototype's shape twice, allocated an array of `max(count,1)` entries even when the answer was zero, and took and released an atom reference per match, once per `for-in` over `Object.prototype`'s shape | A direct non-allocating scan of each prototype's own shape; nothing is retained | Not benchmarked individually; adjudicated with the cumulative stack | No |
| `0085` | Avalanches the Map and Set key hashes | `map_hash_key` mixed with one odd multiply, which cannot clear a trailing zero bit, while `map_find_record` selects its bucket from the low bits, so Maps keyed by numbers or objects degenerated into a linked list | Two mixing steps, one per hashing site | Not benchmarked individually | No |
| `0086` | Grows the property array by doubling | A fixed growth increment reallocates and copies on a fixed schedule, so accumulating an object key by key costs quadratic copying | Geometric growth, making the amortised add constant | Not benchmarked individually | No |
| `0087` | Skips `ArraySpeciesCreate` when it provably ends at a plain array | For an ordinary array the protocol runs a constructor lookup, a constructor test, the cross-realm step, an accessor call for `Array[@@species]` and a construct that re-looks-up the prototype | `js_array_species_is_default()` consulted before the protocol; subclasses, altered `Symbol.species`, Proxy constructors, cross-realm arrays and an altered `Array.prototype.constructor` keep the full path | Not benchmarked individually | No |
| `0088` | Keeps `Object.assign` off the object-spread fast path | `Object.assign` is specified as Set on the target -- it invokes a target setter, walks the target's prototype chain for one, and preserves existing attributes -- while the fast path presumes Define: it inspects the source for accessors and only checks the target for class, exotic behaviour, fast-array layout and extensibility | `Object.assign` takes the generic property-set path; spread keeps the fast path, which is correct because spread creates data properties on a fresh literal | Correctness fix, not benchmarked | No |
| `0089` | Memoizes the `(shape, key) -> index` mapping for element loads after a `for-in` key | A loop of the form `for (k in next) prev[k]` takes the generic route on 91-100% of loads: `JS_ValueToAtom` with a numeric-string scan of the key, a hash probe, and the prototype walk, and the key differs every iteration so no inline cache can reuse anything | One entry per runtime holding a counted reference to the shape, the atom and the index, consulted in the shared element-load path; the reference is what keeps the shape from mutating in place, and a reader re-derives the atom and refuses non-data slots | Not benchmarked individually | No |
| `0090` | Memoizes the `for-in` pin admission scan per shape | The scan walks the shape's whole property table and ran on every `for-in` entry to re-derive an answer that cannot have changed, while a loop nest alternating between two or three shapes is the React case | An eight-slot table indexed by shape address, each slot holding a counted reference to the shape it describes; that reference removes the need for any invalidation hook, and both verdicts are recorded | Not benchmarked individually | No |
| `0091` | Passes the original object as the receiver in the borrowed field load | The prototype walk reassigns the variable holding the borrowed local to the exotic object it stops on, and the slow path then passed that object as the receiver, so a Proxy get trap or a prototype getter saw the prototype instead of the named object | The receiver is saved before the walk and passed at the call site | Correctness fix, not benchmarked | No |
| `0092` | Does not build a stack trace for thrown values that cannot carry one | Frames were collected before it was known whether the value could hold them, so a thrown primitive, plain object or thenable paid for a complete stack walk with string formatting on a path used for control flow | One clause fewer in the existing condition: `needs_backtrace()` decides on its own, so an Error is unaffected and every other value propagates untouched | Not benchmarked individually | No |
| `0095` | Defers Error stack formatting to the first `.stack` read | Building the stack text eagerly spent 87 ns per frame in `dbuf_printf` and 38 ns converting the same filenames, against 13 ns for the walk, and most Errors are never read | An internal class holds the captured frames and the text is produced on first read and memoised; the eager path is kept for `prepareStackTrace`, filters and parse errors | Not benchmarked individually | No |
| `0096` | Takes acyclic function bytecodes off the collector's object list | Half of what the cycle collector traces on a React Native heap is function bytecodes, each visited twice per collection for a single shared edge, and the acyclic ones cannot take part in a cycle | A second object list the collector does not walk, a header bit, and a predicate evaluated at creation and at the two places its mutable terms change; the population is spliced back before the final collection and demotion stops as soon as a second context exists | Not benchmarked individually | No |
| `0097` | Admits lazy function bodies to the untraced set | Deferring a body reserves its constant pool inline from the header, so the pool count is non-zero for a pool that was never written and `0096` admitted under a twentieth of the objects on the precompiled-bytecode path that it admits from source | One predicate term: a pool that is reserved but unwritten is inert because the reader's allocation zeroes it, and a body whose materialization failed is excluded | Not benchmarked individually | No |
| `0098` | Reports the traced GC population and its composition | `obj_count` counts only JS objects while the collector walks every GC type, so a per-object cost computed from it is mis-priced; the ratio between the two is not constant, because function bytecodes are traced from source and untraced from a lazily read blob | Seven counters on the memory-usage structure, taken before the `continue`s that skip most GC types | Not benchmarked individually | No |
| `0099` | Paces cycle collection by whether the last collection reclaimed anything | The rearm was heap-growth alone and never asked whether the collection it paid for was worth running; in a reference-counted engine a collection finds nothing unless the program built a cycle, and splay frees zero over 16 collections | A productivity gate (yield < 1/64 or < 256 KB) doubling the growth step per consecutive unproductive collection, bounded to 400% of the live heap and never tighter than the unmodified 1.5x, shared by both rearm sites and exposed through JS_Get/SetGCPacingCap | Octane geomean +2.74%, splay +39.08%, typescript +4.21%, deltablue -1.97% (historical device run, not re-measured here) | No |
| `0100` | Clears the operand-stack slot before a helper consumes the value it names | Twelve slow-path helpers move the operand's reference into a C local and then convert the other operand, which can run user code, so between the two the slot names a value the helper no longer owns | Nine two-operand sites clear both slots and three single-operand sites clear the one, at the point the reference moves | Not benchmarked individually | No |
| `0101` | Borrows frame receivers for element loads | Computed element reads otherwise duplicate the receiver, push and pop a stack slot, dispatch its load, and release it immediately | A bounded straight-line window scan deletes the receiver load, the element load reads the frame slot directly, and an unconsumed armed rewrite fails compilation | Not benchmarked individually | Yes. The final series-wide bump remains in 9999. |
| `0102` | Borrows frame receivers for element stores | The store path pays the same duplicate, push, dispatch and release, with the receiver pushed before the key and value; reusing the opcode slot also exposes a final-only opcode in the parser's temporary stream | The same scan admits a depth-below receiver and emits one combined store opcode; async iterator close uses primary `undefined; strict_eq` so temporary decoding and jump relocation stay aligned | Not benchmarked individually | Yes. The final series-wide bump remains in 9999. |
| `0103` | Moves the operand-shuffle handlers out of the interpreter's dispatch body | Each inline case declared a temporary and performed the shuffle inside JS_CallInternal, enlarging that function's frame and code on every interpreted call whether or not the shuffle runs | Eight noinline helpers -- perm3, rot3l, rot4l, rot5l, rot3r, perm4, perm5, swap2 -- with a call left in each case | Not benchmarked individually | No |
| `0104` | Moves 25 cold handler bodies out of the interpreter's dispatch body | Each inline case declared its own temporaries inside JS_CallInternal, so every one of them enlarged that function's frame and its register pressure on every interpreted call whether or not it ever ran. Sony SO-01M, Android 11, arm64, six interleaved repetitions per shape | No |
| `0105` | Breaks the closure self-cycle at frame teardown | `var f = function () { ... f ... }` builds a two-object cycle -- the var_ref holds the closure and the closure's var_refs array holds the var_ref -- so neither count ever reaches zero and every one of them waits for a full-heap trial deletion. | `0106` | Retires three element and branch fusions whose A/B was null | Removing each fusion individually measured inside the null floor; removing the three together improved geomean by about 1.3% | Stops emitting `for_in_next_if_false`, `get_arg8_loc8_array_el`, and `get_loc8_array_el`, retaining their numbered slots as reserved opcodes | Host, four rows and five pairs; combined about +1.3% geomean | No |
| `0107` | Adds an experimental register-bytecode backend and interpreter, guarded by `QJS_REGVM` | The operand-stack interpreter pays a frame load and a frame store for every local and argument and a push and a pop for every temporary; a register form removes that traffic at the source, and this is the experiment that decides whether it beats the stack VM on the code react-native-quickjs runs | `quickjs-regvm.h`, `js_regvm_scan`, `js_regvm_build_cfg`, `js_regvm_encode`, `js_regvm_execute`, and the three `builtin-*.regvm.h` blobs | Off by default and not yet faster overall: 71.1 native instructions per bare-loop iteration against the stack VM's 129.1, and Box2D fixed work 65.2 billion instructions against the stack VM's 41.7 billion, but Box2D improved 10.9% (73.2 -> 65.2 billion, wall ~3400 -> ~2970 ms) from giving the interpreter its own function | Yes. | `0109` | Fixes register value aliasing, for-await iterator close, and two reference leaks | After stack shapers became value aliases, `nip` had no definition and the slot-forwarding model still named shaper outputs as fresh values, so `&&=`/`\|\|=`/`??=` results and `yield*` results read stale registers; the for-await step's `dup3; drop` removed the loop's iterator record, so exceptions skipped `return()`; `define_global_func` and `define_method` duplicated values their callees only borrow | `nip` in `regvm_perm_of`, alias-aware slot forwarding, a sentinel drop only on the sentinel's last stack reference, and borrowing calls to `JS_DefineGlobalFunction` and `JS_DefineProperty` | Correctness fix. ## Reading the patches

`patch_viewer.html` renders every `.patch` in this directory side by side, with
the header, the diff and syntax highlighting. Open it from a local server so it
can list the directory, or drag the patch files onto it:

```
python3 -m http.server -d engine/patches
```

## Writing a patch header

Headers are for people. Keep them short -- usually twenty to forty lines --
and say things the way you would say them out loud.

```
Subject: <one sentence saying what this adds>

What this does
  Two to four short sentences.

Why we need it
  What in the current engine is broken or impossible without this.

What it adds
  JS_GetFrameInfoAtLevel()  - asks the engine where a given stack frame is
                              in the source: which file, which line, which
                              column, and the function's name.

Needs a bytecode version bump
  No.

Notes
  Anything a reviewer genuinely needs. Leave it out if there is nothing.
```

Rules:

- Spell acronyms out the first time. Write "the Chrome DevTools debugging
  protocol", not "CDP".
- No decoration. No symbols, no shouting in capitals, no bookkeeping about
  which branch or session produced it.
- Nothing a stranger cannot follow. No references to internal documents, and
  no using a patch number as if it were a name.
- Describe behaviour, not internals. "Lets the debugger ask where each stack
  frame is" beats a paragraph about borrowed atoms. Details like who frees
  what go under **Notes**, if they matter at all.
- If the patch exists for speed, show the measurement.

## No patch bumps the bytecode version

A patch that changes the bytecode format **must not touch `BC_VERSION`**. It
says so in its header and in its README row, and changes nothing.

One patch raises the number, once, for the whole series:

    9999-bc-version-bump.patch

It is numbered `9999` so that adding patches never renumbers it and it always
applies last. Its header lists every patch that made the bump necessary.

The reason is not tidiness. If each patch bumps the version itself, then any
two such patches conflict over the same line for reasons that have nothing to
do with what either one does, and rebasing the series becomes a day's work
instead of a minute's.

The precompiled `builtin-*.h` blobs record the bytecode version in their first
byte, so they are regenerated *after* the tail patch, as part of the projection
step — never inside the patch that changed an opcode.

`scripts/apply-patches.js --check` enforces all of this. It fails if a patch
has no row in this table, if a row names a patch that does not exist, if any
patch other than `9999` touches `BC_VERSION`, or if a patch says it needs a
bump while `9999` is missing.
